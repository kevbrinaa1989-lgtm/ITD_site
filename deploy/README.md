# Подготовка сервера — без публикации

Эти файлы — шаблоны для будущего размещения. Они не подключают сервер, домен, почту или хранилище. Caddy, выпуск настоящего сертификата и внешний репозиторий restic необходимо отдельно проверить при размещении. Сейчас развёртывание не выполнялось.

## Один сервер и закрытые данные

Рекомендуется VPS с постоянным локальным диском, Node.js **24.13 или новее в ветке 24**, Caddy, systemd и restic. Один экземпляр Node; не используйте общий сетевой диск для SQLite. Доступные извне порты — HTTPS 443 и HTTP 80 для перенаправления/получения сертификата; порт Node 8000 извне закрыт.

1. Создайте отдельного системного пользователя `itd-studio` с домашней папкой `/var/lib/itd-studio`. Каталог данных и домашняя папка — владелец этот пользователь, права `0700`. Код разместите в `/opt/itd-studio/current`, без права записи для пользователя приложения. Не помещайте данные в папку публичных файлов.
2. Переносите только проверенную полную резервную копию, а не `storage.json` с путями Windows. Восстановите её в **новую** папку штатной командой `node storage-cli.mjs restore "копия" "новая-папка"`, затем подключите `node storage-cli.mjs bind "новая-папка"`. Обе операции выполняйте под `itd-studio` с `HOME=/var/lib/itd-studio`. Настройки находятся в `/var/lib/itd-studio/.itd-studio/storage.json`. Не запускайте первоначальную настройку вместо восстановления.
3. Скопируйте `app.env.example` в `/etc/itd-studio/app.env`, укажите реальный HTTPS-адрес в `PUBLIC_ORIGIN`. Файл принадлежит root, права `0600`. Интернет-режим принудительно включает Secure-cookie; для локального запуска Windows он не требуется.
4. Подготовьте Caddyfile с тем же доменом. Caddy передаёт исходный Host и **сам устанавливает** `X-Real-IP` и HTTPS-протокол; чужие `X-Forwarded-For` не используются. Не добавляйте CDN или ещё один прокси без отдельной настройки доверия. Node слушает только `127.0.0.1:8000`.
5. Установите `itd-studio.service` в `/etc/systemd/system/`. Проверьте путь `/usr/bin/node`, доступ пользователя к данным, затем конфигурацию через `systemd-analyze verify`. Включение сервисов, изменение DNS и запуск HTTPS выполняются только после отдельного разрешения на публикацию. systemd перезапускает Node при сбое; журналы: `journalctl -u itd-studio`.

## Ежедневная зашифрованная внешняя копия

`itd-backup.timer` запускает работу ежедневно около 03:30 по часовому поясу сервера. Время и разброс задаются в timer. Доступность приложения кратко прерывается: скрипт останавливает сервис, создаёт **полную проверенную копию SQLite и документов** под тем же пользователем, затем запускает сервис. Только после запуска отправляет копию через restic, который шифрует её **до передачи**, проверяет репозиторий и применяет сроки хранения. Неудачная отправка/проверка не запускает удаление предыдущих внешних копий.

- Создайте закрытую папку `/var/lib/itd-studio/backups` владельца `itd-studio`. Настройте отдельный внешний репозиторий restic; платное хранилище не подключено. Самостоятельно выполните `restic init` с нужными безопасными настройками при разрешённом размещении.
- Скопируйте `backup.env.example` в `/etc/itd-studio/backup.env`: root, `0600`. Это доверенный shell-файл. Задайте внешний репозиторий и путь к файлу пароля. Реальные пароль шифрования и ключи провайдера храните отдельно от кода, root-only `0600`; резервный экземпляр пароля храните вне сервера. Без него восстановить зашифрованную копию невозможно. Файл ключей провайдера может содержать `export` необходимых restic переменных.
- Установите backup service и timer из этой папки. Перед расписанием выполните контролируемый пробный запуск и восстановление на вымышленных данных. Скрипт использует `flock`; параллельные запуски запрещены.
- При обычной ошибке и сигналах TERM/INT срабатывает возврат сервиса. На случай принудительного завершения процесса `ExecStopPost` проверяет отметку необходимости запуска и запускает приложение. После отключения питания приложение запускает обычный включённый systemd-сервис. Проверьте эти сценарии на целевом сервере.
- Сбой виден по ненулевому результату, в `systemctl --failed` и `journalctl -u itd-backup`. Это локальное сообщение об ошибке, а не уведомление владельцу по email: настройку мониторинга журнала/свободного места выполняет оператор при размещении. Если повторный запуск не удался, журнал содержит `CRITICAL`.
- `KEEP_DAILY`, `KEEP_WEEKLY`, `KEEP_MONTHLY` задают хранение нескольких внешних копий. После успешной отправки и проверки локально остаются `KEEP_LOCAL` последних проверенных копий (по умолчанию две, включая текущую). Очистка ограничена непосредственными проверенными папками `ITD-…` внутри отдельного каталога резервирования; ссылки, неизвестные и неполные папки не удаляются. После сбоя очистка не выполняется: контролируйте свободное место. Снимки миграции также требуют места.

## Восстановление

Остановите приложение. С помощью restic восстановите выбранную внешнюю копию в отдельную закрытую временную папку, найдите папку с `backup.json`, `itd.sqlite` и `files`. Выполните `node storage-cli.mjs verify "папка-копии"`, затем `restore` в **новую** папку. Исходную копию не заменяйте. При восстановлении только в новой базе удаляются сессии и аннулируются ссылки восстановления пароля и активные приглашения; пользователи, пароли, доступ к проектам и документы сохраняются. Восстановленная папка получает собственное проверяемое описание копии. Обычный запуск эти действия не выполняет.

Подключите новую папку штатным способом под пользователем службы; если уже подключены прежние данные, сначала отдельно согласуйте переключение, не удаляйте настройки вручную. После запуска всем потребуется снова войти; новые ссылки создаются администратором. Проверьте проект, файл, согласования и вход на отдельном тестовом восстановлении.

`migration-snapshots/…/itd.sqlite` — **только снимок базы перед изменением структуры**. Он не содержит документы и не заменяет полную копию. Не копируйте его поверх рабочей базы вручную.
