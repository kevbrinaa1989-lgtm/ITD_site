# Make: только ITD Studio

Это инструкция настройки существующего сценария **Integration Webhooks**. Его изменения из этой среды не выполнялись: нет подключённого доступа к Make, Google Sheets и Telegram. Существующий URL вебхука не копируется в публичные файлы. Работа со старым сайтом не требуется.

## Маршруты

Custom Webhook → проверка/учёт request_id → Router:

- `form_type = calculation_request` → лист «Заявки» → уведомление Telegram.
- `form_type = design_questionnaire` → лист «Анкеты» → уведомление Telegram.

Оба маршрута дополнительно проверяют `source_site = itdstudio.ru`. Не заменять эти значения другими названиями. Ненужные ветки прежнего сайта можно отключить после сохранения экспорта текущего сценария.

Настроить последовательную обработку webhook-сценария, чтобы два одинаковых request_id не проходили проверку одновременно. Включить хранение незавершённых выполнений и обработку ошибок без фиктивного ответа об успехе.

## Поля

Общие: `request_id`, `form_type`, `submitted_at` (ISO 8601), `name`, `phone`, `contact_method`, `area`, `page_url`, `source_site`, `consent`.

Короткая заявка дополнительно передаёт, когда применимо: `package`, `calculator_area`, `calculated_total`, `supervision`, `project_name`, `project_view`, `context`. Неизвестные данные отсутствуют или пустые. Стоимость берётся из существующих правил калькулятора, а не вычисляется в Make повторно. `supervision` — false или объект `{selected:true,months,monthly_from}`.

Анкета дополнительно передаёт `email`, `object_type`, массивы `styles`, `services`, `answers_text`, `answers_json`.

Полный `answers_json` содержит: `object_type`, `object_address`, `area`, `rooms`, `stage`, `docs`, `residents`, `pets`, `needs`, `styles`, `likes`, `redev`, `services`, `budget`, `start`, `comments`, `name`, `phone`, `email`, `method`. Множественный выбор сохраняется массивами, не только первым вариантом. `answers_text` содержит все те же вопросы с русскими подписями.

Значение `request_id` нужно сохранять и в таблице, и в состоянии обработки Make. `submitted_at` хранить как исходную строку; отображение времени таблицы можно установить «Москва». Желательно добавить собственную дату приёма Make отдельной колонкой, не подменяя исходное время.

## Без повторных строк и уведомлений

Для каждого request_id хранить состояние шагов: запись в таблицу и отправка сообщения. Перед созданием строки искать request_id; найденную строку не создавать заново. Использовать текстовый формат ячеек / режим RAW: содержимое ответа, начинающееся с `=`, `+`, `-` или `@`, не должно становиться формулой.

После подтверждённой записи сохранить номер строки. После подтверждённого Telegram-сообщения сохранить message_id. При повторном обращении с завершённым request_id вернуть тот же успешный ответ без повторной записи и сообщения. Если одинаковый request_id пришёл с другим содержимым, отклонить его.

Если Make потерял подтверждение Telegram после фактической отправки, нельзя надёжно обещать «ровно одно» сообщение: Telegram Bot API не предоставляет ключ идемпотентности sendMessage. Не включать слепую повторную отправку для такого неопределённого случая. Проверить историю выполнения и сообщение. Серверный обработчик из комплекта тоже не повторяет сомнительную отправку автоматически. Это сознательная защита от дублей, а не гарантия автоматического устранения любого сбоя.

## Длинные анкеты

Не обрезать answers_text/answers_json. Google Sheets ограничивает размер одной ячейки (около 50 000 символов), Telegram — длину одного сообщения (4096 символов). Для обычных анкет достаточно основных колонок и полной JSON-строки. До реального запуска проверить длинный ответ.

Для превышения размера ячейки настроить сохранение текста/JSON частями, например по 20 000 символов, в дополнительные строки с тем же request_id, типом содержимого и номером части. Это лучше, чем молча потерять конец ответа. Количество частей также сохранить в основной строке. Не ограничивать число частей без явной ошибки. Можно использовать дополнительный лист «Ответы» только если действующие колонки не позволяют сохранить полные данные.

Telegram отправляет краткое уведомление: тип, ID, имя, контакт, параметры объекта и ссылка на запись таблицы. Все ответы остаются в таблице; необязательно дублировать огромную анкету в чат. Отключить parse_mode либо экранировать пользовательский текст. Не вставлять неэкранированные ответы в HTML/Markdown сообщения.

## Подтверждение на сайте

В конце **каждой** ветки после успешной записи Google Sheets и отправки Telegram поставить **Webhooks → Webhook response**:

HTTP status: `200`

Content-Type: `application/json`

Body (request_id подставляется из полученного запроса):

```json
{"ok":true,"request_id":"полученный request_id","delivery":{"sheets":true,"telegram":true}}
```

Не возвращать такой ответ до выполнения модулей. Обычное стандартное `Accepted` от Make не считается подтверждением: сервер вернёт ошибку, а сайт не покажет фиктивное «получено».

При ошибке вернуть не-2xx, сохранить незавершённое выполнение для разбора. Если процесс занимает дольше настроенного тайм-аута, сайт покажет ошибку и сохранит данные; это нужно проверить до публикации. Для долгих сценариев потребуется отдельный подтверждённый механизм очереди/проверки статуса, которого в текущем сценарии нет.

## Реальная приёмка — ещё требуется

На вымышленных данных с пометкой ТЕСТ проверить: обычную заявку, калькулятор, обращение из портфолио, все пять шагов анкеты, множественный выбор, длинный текст и повтор того же request_id. Для каждого проверить строку Google Sheets, Telegram и итоговый JSON. Проверить ошибку каждого модуля и восстановление после неё. Только после этой проверки включать обработчик на публичных страницах.
