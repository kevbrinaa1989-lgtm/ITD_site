# Обработчик форм: отдельная серверная программа

Код Tilda работает в браузере и не умеет хранить секрет вебхука. Этот обработчик запускается отдельно на Node.js 24, за HTTPS-прокси. Он не обращается к базе личного кабинета. Сервер и сервисы автоматически не создаются.

## Подключение

1. Выберите существующий сервер с постоянным диском. Отдельно согласуйте размещение; этот комплект пока никуда не опубликован.
2. Установите Node.js 24. Создайте закрытую папку вне публичного сайта под служебную базу заявок. База хранит только идентификатор, хеш запроса, состояние и время; ответы посетителей в ней не сохраняются.
3. Задайте переменные из `env.example` средствами хостинга. `MAKE_WEBHOOK_URL` хранится только на сервере. Не вставляйте его в Tilda или GitHub. `ITD_FORMS_DB` — абсолютный путь к отдельной служебной базе; не указывайте базу личного кабинета.
4. Запустите `node integration/server.mjs`. Процесс слушает только `127.0.0.1:8081`. На сервере нужен один экземпляр с автоматическим перезапуском. Блокировка SQLite не допускает одновременные экземпляры на одной служебной базе и освобождается ОС после сбоя.
5. Используйте HTTPS-прокси. Пример — `Caddyfile.example`. Для него включите `ITD_TRUST_LOCAL_PROXY=1`: только локальный прокси может сообщить IP посетителя, `X-Real-IP` обязательно перезаписывается. Не добавляйте ещё один CDN/прокси без адаптации доверия. Не открывайте порт 8081 извне. Если режим выключен, заголовки IP игнорируются; лимит применяется к непосредственному подключению (за прокси это будет общий лимит).
6. В публичной конфигурации сайта укажите URL **обработчика** `/api/forms`, а не секрет Make. Разрешён источник только `https://itdstudio.ru`.
7. Настройте Make согласно `MAKE-SETUP.md` и проверьте оба маршрута вымышленными данными. Затем проверьте ответы браузера и записи Google Sheets/Telegram.

## Подтверждение и защита от дублей

Сайт передаёт случайный `request_id` и повторяет тот же идентификатор и снимок данных при повторной попытке. Одновременные одинаковые запросы не уходят в Make дважды. Уже подтверждённый запрос возвращает успешный ответ из служебной базы даже после перезапуска.

Обычного ответа Make `Accepted` недостаточно. После успешной записи Google Sheets **и** отправки Telegram сценарий должен вернуть HTTP 200 и JSON:

```json
{"ok":true,"request_id":"ИДЕНТИФИКАТОР ИСХОДНОГО ЗАПРОСА","delivery":{"sheets":true,"telegram":true}}
```

Роутер должен сохранять `calculation_request` и `design_questionnaire`. Источник принудительно `itdstudio.ru`. Полный JSON анкеты и текст не обрезаются; запрос свыше 1 МиБ отклоняется целиком. Если текст превышает ограничения ячейки Google Sheets или сообщения Telegram, сценарий обязан сохранить все части (см. `MAKE-SETUP.md`). Ограничение HTTP-ответа Make — 64 КиБ.

## Сбой связи: важное ограничение

Если после обращения к Make нет достоверного ответа, обработчик не знает, успели ли записаться данные. Он сохраняет состояние `unknown`, показывает ошибку и **не посылает такую заявку повторно вслепую**. Это исключает повторный запуск, но такая ситуация требует проверки истории Make по `request_id`. Не удаляйте запись и не выдавайте новый идентификатор, пока не установлено, что предыдущая операция не создала записи/уведомления.

Повторная попытка после ошибки до отправки (например, временно отсутствующей конфигурации) работает. После подтверждённого успеха повтор возвращает тот же успех. Полностью автоматическое восстановление после неопределённого результата потребует проверенного механизма идемпотентности и статуса в реальном Make. Этот этап нельзя объявить выполненным без доступа к сценарию.

Программа не пишет контакты, ответы, секрет вебхука или полное тело ошибки Make в журнал. Лимит — 8 запросов за 10 минут с IP, включая повторы. Он сохраняется после перезапуска. Поле-ловушка отсеивает часть автоматического спама, но не заменяет полноценную антибот-защиту.

## Локальные тесты

Из папки комплекта выполните `node --test integration/relay.test.mjs`. Используются временная база и имитация Make, без отправки настоящих запросов.
