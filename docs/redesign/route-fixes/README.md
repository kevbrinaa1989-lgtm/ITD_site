## Правила этапов и прогресса

Единая функция выбирает текущий этап в порядке проекта: сначала «В работе» / «Нужны изменения», затем «На согласовании», затем первый запланированный. «Согласован» и «Завершён» не выбираются текущими. Файлы не участвуют в выборе этапа. Если параллельно выполняется несколько этапов, они остаются доступны, а материалы других этапов не теряются из очереди решений заказчика.

Процент обозначает **долю согласованных или завершённых этапов**, а не трудозатраты и не полное завершение проекта. Каждый этап учитывается один раз: `(approved + completed) / количество этапов`, с округлением. Рядом отдельно видны количества согласованных и завершённых. Правило одинаково на главной заказчика, в списке проектов и шапке рабочего пространства обеих ролей. Если все этапы только согласованы, интерфейс поясняет, что завершение ещё отмечает студия.

Завершение — явное действие администратора: **Этапы → Редактировать этап → Статус этапа: Завершён → Сохранить этап**. Используется существующий `PATCH /api/stages/:id`. Согласование файла сохраняет действующую серверную логику согласований; новых автоматических переходов нет. Просмотр и обновление страниц не записывают статусы. Согласование версии файла и завершение этапа остаются отдельными сущностями.

Для старых материалов, чьё название совпадает с именем загруженного файла, отображается стабильное обозначение по этапу и номеру материала. Если API предоставляет отдельное логическое название, оно сохраняется. Переименование записей в базе не выполняется; оригинальные имена доступны в просмотре и скачивании выбранной версии. У обычного файла без истории версий номер версии не выдумывается.

## Как повторить и установить на тестовый стенд

Используйте Node.js 24.13+ (ветка 24) и Chromium/Playwright. Не запускайте приложение с продуктивными настройками или папкой данных.

```bash
npm test
npm install --no-save --package-lock=false playwright@1.58.2
npx playwright install chromium
export ITD_CHROMIUM="$(node --input-type=module -e 'import {chromium} from "playwright"; console.log(chromium.executablePath())')"
export ITD_SCREENSHOT_DIR="test-results/route-fixes"
node tests/browser-route-fixes.mjs
```

Тест сам создаёт приложение и базу во временной папке, загружает фикстуру изображения и удаляет только свою временную папку в конце. Для снимков в этом отчёте передан `ITD_BROWSER_IMAGE` — ранее сохранённая публичная визуализация ITD Studio; без него тест использует встроенную JPG-фикстуру. Режим `ITD_CAPTURE_BASELINE=1` предназначен только для снимков исходной версии и не проверяет наличие исправлений.

## Публикация и откат

**На VPS ничего не публиковалось; продуктивная SQLite не открывалась и не менялась.** Изменений схемы, миграций, массовой записи статусов или конфигурации VPS в этом PR нет. Серверное изменение ограничено раздачей нового статического `project-state.js`.

Будущую публикацию выполнять только по отдельной команде владельца. После разрешения оператор использует [существующую процедуру резервного копирования, проверки копии, обновления и отката](../UPDATE-AND-ROLLBACK.md), выбирая уже проверенный коммит этой ветки. Зафиксировать текущий установленный релиз и проверить резервную копию до переключения. Перенести весь согласованный комплект HTML/JS/CSS, включая `project-state.js` и его маршрут в `server.mjs`, затем проверить вход и семь этапов. При проблеме вернуть прежний релиз кода. Откат интерфейса не требует восстановления старой базы и не должен уничтожать решения/комментарии, появившиеся после обновления.
