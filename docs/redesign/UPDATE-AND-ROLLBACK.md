# Тестовая установка, обновление и откат «Маршрута»

Это инструкция для оператора. Она **не выполнялась на VPS**. Публикация на `lk.itdstudio.ru`, изменения службы/прокси и продуктивных данных требуют отдельного поручения владельца.

Редизайн основан на `feature/client-cabinet` (исходный коммит `99b7555`). PR направлен в эту ветку: основной `main` ещё не содержит действующую серверную часть кабинета. Не заменяйте произвольную старую установку поверх `main`. Сначала сравните установленную версию и состав данных с указанной базой. Изменений схемы SQLite, правил доступа и серверных согласований в редизайне нет; существующие серверные миграции базовой ветки не удалены.

## Сначала — отдельная тестовая установка

1. Используйте Node.js 24.13+ в ветке 24. Получите ветку `feature/itd-superdesign-redesign` в отдельную папку кода. Не копируйте туда рабочую базу, настройки `storage.json` или `.env`.
2. В папке кода выполните `npm test`. Проверки сами создают временные базы и удаляют только свои временные папки.
3. Для браузера установите инструменты: `npm install --no-save --package-lock=false playwright@1.58.2`, затем `npx playwright install chromium`. Запустите тесты ниже. Если в системе нет библиотек Chromium, оператор тестовой машины может использовать `npx playwright install --with-deps chromium`.

```bash
export ITD_CHROMIUM="$(node --input-type=module -e 'import {chromium} from "playwright"; console.log(chromium.executablePath())')"
export ITD_SCREENSHOT_DIR="test-results/screenshots"
node tests/browser-route.mjs
node tests/browser-review.mjs
node tests/browser-workspace.mjs
node tests/browser-preview.mjs
node tests/browser-admin.mjs
node tests/browser-approved-interface.mjs
node tests/browser-upload-context.mjs
node tests/browser-invitations.mjs
node tests/browser-recovery.mjs
```

Успех — каждая команда завершилась с кодом 0 и строками `PASS`. Это настоящие API и временная SQLite, не подмена ответов макета. Браузерные тесты запускают сервер только на `127.0.0.1` и блокируют внешние запросы. Для ручной проверки на тестовом сервере используйте отдельного системного пользователя с отдельными домашней папкой, настройками и данными; никогда не запускайте первоначальную настройку под рабочим пользователем службы.

4. После отдельного разрешения на работу с копией клиентских данных можно восстановить **проверенную полную резервную копию** в новую закрытую тестовую папку. Используйте `verify` и `restore`, описанные ниже. Тестовая установка должна быть закрыта от посторонних, не отправлять сообщения клиентам и не использовать рабочие настройки.
5. Войти двумя ролями, проверить проекты/этапы, документы, историю JPG → PDF → JPG, выбранные версии, комментарии, согласование и отмену, уведомления, задачи, клиентов и мобильную форму. Убедиться, что решения и комментарии остаются после перезапуска тестовой службы.

## Подготовка будущего обновления VPS

До остановки сервиса оператор фиксирует установленный коммит, путь к предыдущему релизу, пользователя службы, домашнюю папку, Node, папку данных и резервных копий. Проверяет свободное место и возможность возврата. Секреты из конфигурации не публикуются в PR/журналах.

В репозитории приведён **шаблон**, а не обследованная конфигурация VPS: служба `itd-studio.service`, пользователь `itd-studio`, код `/opt/itd-studio/current`, домашняя папка `/var/lib/itd-studio`. Если фактическая установка отличается, команды адаптирует оператор. Не заменяйте настройки сервера шаблонами из `deploy/`.

Подготовить новый релиз в отдельной папке, например `/opt/itd-studio/releases/<утверждённый-коммит>`, включая `assets/fonts`, `assets/brand`, `vendor/pdfjs`, новые JS/CSS и весь существующий серверный код. Проверить на тестовой установке именно этот коммит. Папка данных остаётся вне папки релиза. Не выполнять `data:init`, повторный `bind`, ручные SQL-команды, очистку или импорт демонстрационных данных.

## Полная копия перед переключением

Только после отдельного разрешения на обновление, в согласованное окно обслуживания:

1. Исключить параллельное резервирование и автоматический перезапуск приложения другими заданиями: дождаться окончания уже запущенной копии и временно приостановить её расписание штатным способом. Зафиксировать, как вернуть расписание после обновления или отмены. Остановить рабочую службу, проверить, что все экземпляры старого Node завершились. Не копировать работающую SQLite обычным `cp`.
2. Запустить штатное резервирование из **старого релиза**, под тем же пользователем и с той же домашней папкой, что у рабочей службы. Пример для шаблонной установки:

```bash
sudo systemctl stop itd-studio.service
sudo -H -u itd-studio /usr/bin/node /opt/itd-studio/current/storage-cli.mjs backup /var/lib/itd-studio/backups
```

Команда напечатает путь конкретной копии `ITD-…`. В ней должны быть `backup.json`, `itd.sqlite` и `files`. Проверить именно этот путь:

```bash
sudo -H -u itd-studio /usr/bin/node /opt/itd-studio/current/storage-cli.mjs verify /var/lib/itd-studio/backups/ITD-<имя-полученной-копии>
```

3. Сохранить всю проверенную копию отдельно от VPS штатным настроенным способом резервирования. Сохранить прежний релиз и конфигурацию. Если копирование/проверка не завершились успешно, **не переключать код**, запустить прежнюю службу и выяснить причину. Не оставлять сайт остановленным после ошибки резервирования.
4. При схеме с символьной ссылкой `current` переключить её на проверенный новый релиз атомарно. Если `current` — обычная папка, не заменять её ссылкой автоматически: использовать существующую процедуру установки. Настройки systemd/Caddy/домена/данных остаются прежними.
5. Запустить службу. Проверить `systemctl status itd-studio.service` и журнал `journalctl -u itd-studio.service --since '-5 minutes'`. Пройти вход, проекты, загрузку изображений/PDF и чтение истории. Проверку создания решения выполнять на специально разрешённом тестовом проекте; не согласовывать реальные материалы ради проверки.

## Откат кода

Если новый интерфейс не работает: остановить службу, вернуть `current` на сохранённый предыдущий релиз и запустить службу. **Не восстанавливать базу ради отката CSS/JS**: новых миграций в редизайне нет, а восстановление старой копии потеряет решения и комментарии, сделанные после обновления. Проверить вход, проекты, версии и скачивание оригинала.

## Аварийное восстановление данных

Только при подтверждённой проблеме данных и отдельном согласовании допустимой потери изменений после копии. Остановить службу и сохранить текущие данные для разбора. Проверить копию, затем восстановить её в **новую несуществующую папку**:

```bash
sudo -H -u itd-studio /usr/bin/node /opt/itd-studio/current/storage-cli.mjs verify /var/lib/itd-studio/backups/ITD-<имя-копии>
sudo -H -u itd-studio /usr/bin/node /opt/itd-studio/current/storage-cli.mjs restore /var/lib/itd-studio/backups/ITD-<имя-копии> /var/lib/itd-studio/restored-<дата>
```

Не удалять прежнюю папку и не копировать файлы поверх неё. `restore` не переключает уже настроенную рабочую установку: переключение на восстановленную папку оператор согласует и выполняет отдельно. После восстановления сессии и активные одноразовые ссылки отзываются; пользователи входят заново. Пароли, проекты, файлы, версии, решения и комментарии из копии сохраняются. Подробности штатного резервирования — [deploy/README.md](../../deploy/README.md).
