# ITD Studio: аудит кабинета перед проектированием

Основа: ветка `feature/client-cabinet`, коммит `99b7555`. Рабочая ветка исследования: `feature/itd-superdesign-redesign`.

Это аудит кода и структуры интерфейса. Авторизованные экраны действующего сервера не открывались, реальные данные не использовались. Ни ошибки отображения на конкретном телефоне, ни нарушение доступа, ни совпадение рабочего сервера с этим коммитом здесь не утверждаются. Макеты Superdesign пока не созданы: авторизация инструмента заблокирована ответом 403. Приложение и база не изменены.

## Что уже существует

Приложение на Node.js 24 и SQLite, без UI-фреймворка. HTML содержит оболочку и панели; отдельные JS-модули строят карточки и формы. Есть серверные проверки прав, версии файлов, оптимистическая проверка revision при решениях, приглашения, восстановление пароля через администратора, безопасная привязка загрузки к проекту, локальный PDF-просмотрщик и отдельный механизм резервных копий.

Администратор уже получает рабочую панель с реальными показателями, списком действий студии, ожидающими клиента материалами, задачами и сроками. Клиент уже получает отдельную главную, свои проекты и очередь согласования. Не нужно создавать эти механизмы заново: задача дизайна — сделать существующие данные понятнее.

## PDF/JPG: что уже защищено и что действительно нужно изменить

Данные в базе уже разделены на `review_materials.title`, `review_versions.fileId/versionNumber` и `files.name/contentType/path`. API подробностей отдаёт отдельный объект файла версии (`material-review.mjs:125`). Сервер скачивает файл по ID и формирует Content-Type/Content-Disposition из сохранённых данных этого файла (`server.mjs:633–649`). Предпросмотр отдельно проверяет допустимые типы и содержимое (`server.mjs:24`).

Следовательно, по текущему коду нет основания утверждать, что JPG физически отдаётся как PDF из-за заголовка материала. Подтверждённое смешение — прежде всего модель представления: `versionFileName` создаёт синтетическое имя из старого заголовка и нового расширения, а `presentedFile` передаёт его и просмотрщику. Оригинальное имя показывается лишь в раскрывающемся блоке.

В реализации нужно проверить тестом цепочку: материал с логическим названием → v1 PDF → v2 JPG → возврат v1 → просмотр и скачивание каждой версии. Заголовок, MIME, расширение, байты и имя скачивания должны описывать разные сущности явно и согласованно. Для этого не требуется переписывать существующие файлы или историю. Решение о новом редактируемом логическом названии и возможном необязательном поле принимается после дизайна и проверки совместимости.

## Что обязательно сохранить

- `expectedRevision`, запрет решений по старой версии, подтверждение согласования, обязательный комментарий для изменений (`material-review.js:403–440`, material-review.mjs).
- Серверные права проекта/версии/файла; выключенный аккаунт и переназначение проекта должны закрывать доступ.
- `ITDUploads.allowSwitch`, серверный upload intent и проверка клиента проекта, защита новой версии (`cabinet.js:250`, `material-review.js:476`).
- Реальный просмотр отмечается после отображения, а не после открытия карточки (`material-review.js:671`).
- Сохранение масштаба изображения в текущей сессии просмотра, PDF.js внутри проекта, скачивание оригинала (`file-viewer.js`).
- Различие прочитанного уведомления и незавершённого действия. Рабочий центр уже вычисляет ответы по событиям и версии, а не по readAt уведомления.
- Постоянный путь данных, резервные копии, токены и роли: это вне косметического редизайна.

## Мобильные гипотезы для проверки

В коде есть адаптивные правила до 1000/760/390 px, переносы длинных слов, складывание кнопок решения в колонку. Это положительная основа, но не доказательство отсутствия перекрытий.

На 360/390/768/1024/1440 проверить: длинное название без пробелов; 50+ материалов; переключение выбранной версии; клавиатуру в комментарии; открытый просмотрщик PDF; масштаб и поворот устройства; возврат к материалу; боковое меню и фокус; увеличение системного шрифта; ошибки связи. Для ключевых действий проектировать цель нажатия от 44 px и проверять реальный размер, не только высоту CSS.

## Рекомендуемая структура для макетов

Администратор: Главная → Проекты → Клиенты → Задачи. Уведомления и доступ/восстановление — служебная область. Главная начинается с реальных действий студии, затем сроки, отдельно ожидание клиента.

Клиент: Главная → Мои проекты → Решения → Документы/профиль в соответствующем контексте. Главная показывает текущее состояние проекта и конкретное требуемое решение либо «Сейчас от вас ничего не требуется».

Проект: Обзор → Этапы → Материалы → Документы. «Согласования» можно представить как фильтр/очередь библиотеки, сохранив прямой вход из глобальных решений. Решение о названии и количестве вкладок утвердить на макетах.

Материал: компактный список слева → один выбранный материал → выбранная версия → предпросмотр → решение/обсуждение. История вторична; текущая и историческая версия различимы до нажатия действия. На телефоне сохранить эту же последовательность отдельными экранами, не уменьшать настольные колонки.

## Приёмка до масштабной реализации

1. Получить актуальный визуальный референс itdstudio.ru; старую статическую сборку не выдавать за текущий бренд.
2. Создать настоящие варианты и экраны в Superdesign после восстановления авторизации. Показать desktop/mobile: обзор администратора, обзор клиента, библиотеку, материал PDF→JPG, решение и комментарии.
3. Пользователь утверждает выбранную концепцию. До этого код приложения не изменять.
4. Реализация небольшими этапами с исходным набором тестов плюс тестами метаданных, версии, прав, конфликтов и визуальными сравнениями. Все данные вымышленные.
5. Pull Request, резервная копия и план отката. Развёртывание на рабочем VPS требует отдельного разрешения.
