# Исправление принадлежности документов проектам и этапам

Ветка `fix/document-ownership`, база `2a6dfcce8a1b1fb2e42f1f85831cbf6973ee4f83` из `feature/project-file-library`. Навигация «Обзор / Файлы проекта / Согласования», семь этапов и действующая галерея сохранены. Работа выполнена на изолированных тестовых данных; VPS и продуктивная база не использовались.

## Обнаруженные причины

1. Область библиотеки была обычным фильтром `stage`, который пользователь или сброс фильтров могли очистить. После этого список показывал файлы всех этапов. Это ошибка отображения, а не доказательство неверной записи конкретного продуктивного файла.
2. Защищённая квитанция загрузки закрепляла сессию, администратора, проект и клиента, но не этап. Этап брался из изменяемого поля формы при отправке. Сервер проверял принадлежность этапа проекту, однако смену на другой этап того же проекта между выбором и отправкой файла не отвергал.
3. В SQLite независимые внешние ключи `files.projectId` и `files.stageId` не гарантировали, что этап принадлежит именно этому проекту. Не было транзакционной операции перемещения или переименования.
4. `review_materials.stageId` и `review_events.stageId` требовали этап. Это мешало перенести согласуемый материал в общие файлы проекта вместе с историей.

Без доступа к разрешённой копии продуктивной базы нельзя установить, есть ли в ней фактически повреждённые связи. Для этого добавлен отдельный аудит без записи. Неоднозначные записи не распределяются автоматически.

## Реализованное поведение

- «Файлы проекта» содержит только файлы выбранного проекта без этапа, любых поддерживаемых категорий. Вход в альбом/документы через этап фиксирует этот этап. Поиск, сортировка и сброс фильтров не меняют принадлежность списка.
- Список дополнительно читается через серверный запрос с точным проектом и этапом. Запоздавший ответ другого проекта/этапа игнорируется. Галерея использует актуальную подборку файлов своей области.
- Место загрузки задаётся точкой входа и показано в форме; поле этапа заблокировано. При выборе новой области подготовленная очередь отменяется только после явного подтверждения. Квитанция сервера закрепляет этап; попытка отправки в другой этап/проект отвергается до записи.
- Администратор может переименовать и переместить файл между общими файлами и этапами одного проекта. Для документа меняется логическое название, реквизиты и исходное имя сохраняются. У обычного файла сохраняется расширение. Для согласуемого материала меняется его название и переносится сразу вся группа версий.
- Перемещение обновляет существующие записи: идентификаторы, оригиналы на диске, комментарии, решения, просмотры и уведомления сохраняются. Перемещение само по себе не меняет статусы этапов; старые события сохраняют историческую привязку, новые используют актуальную.
- Переименование и перемещение проверяют ожидаемую исходную принадлежность; устаревшая форма получает ошибку обновления. Межпроектные переносы отсутствуют. Удаление требует подтверждения; файлы истории согласования по-прежнему защищены от удаления.

## База и API

Существующие таблицы `files`, `document_cards`, `review_materials`, `review_versions`, `review_events` используются без параллельной системы документов.

Миграция разрешает `NULL` в `stageId` только у `review_materials` и `review_events`. Она проверяет связи и целостность базы, создаёт снимок SQLite с проверкой всех записей, пересоздаёт эти две таблицы транзакционно, сохраняет индексы и неизменяемость истории, повторно проверяет внешние ключи. При ошибке структура и данные откатываются; режим внешних ключей восстанавливается. Проверка неоднозначных связей происходит до изменения схемы.

Добавлены триггеры SQLite: этап файла/материала обязан принадлежать его проекту; проект уже созданного файла/этапа/материала нельзя незаметно заменить; версии принадлежат одной области материала; перенос материала обновляет все его файлы; новые события соответствуют материалу и версии. Исторические события не переписываются.

| Метод и маршрут | Назначение |
| --- | --- |
| `GET /api/projects/:id/files` | Только файлы без этапа; `?stageId=none` эквивалентен отсутствию параметра |
| `GET /api/projects/:id/files?stageId=:stageId` | Только файлы указанного этапа этого проекта; необязательный `category=result/document` |
| `PATCH /api/projects/:id/files/:fileId` | `stageId` и/или `title`; обязательный `expectedStageId`, при переименовании — `expectedTitle` |
| `DELETE /api/projects/:id/files/:fileId` | Удаление с проверкой `expectedStageId`; история согласований защищена |
| `POST /api/projects/:id/upload-intents` | Принимает `stageId` (NULL для проекта), проверяет его и закрепляет в квитанции |

Существующие скачивание/предпросмотр, согласования и агрегат проекта сохранены. Агрегат проекта содержит его файлы всех этапов для обзора и согласований; библиотека не использует его как общий неограниченный каталог. Все операции проверяют права сервером. Клиент не может изменять файлы или получать файлы чужого проекта. Внешние интеграции загрузки должны передавать выбранный `stageId` уже при получении квитанции; отсутствие означает общие файлы.

## Безопасная публикация — только после отдельного разрешения

Эта инструкция не выполнялась на VPS. В отличие от предыдущего PR библиотеки, здесь **есть миграция**; прежнее утверждение «миграций нет» к этому релизу не относится.

1. Оператор фиксирует текущий коммит, каталог кода, пользователя службы, путь базы/загрузок, настройки и процедуру возврата. Сверяет текущую установку с базой этого PR. Не заменяет настройки сервера шаблонами.
2. На согласованной копии данных запускает аудит: `node file-ownership-audit.mjs /absolute/path/to/copy/itd.sqlite`. Команда открывает базу только для чтения; результат содержит идентификаторы проблемных записей. Пустые `issues` и `foreignKeys` и код завершения 0 означают отсутствие выявленных нарушений. При неоднозначных записях публикацию остановить, сохранить отчёт и согласовать принадлежность; не назначать этапы наугад.
3. Создаёт полную штатную резервную копию SQLite и папки оригиналов, проверяет её `storage-cli.mjs verify`, хранит копию отдельно. Подробности — [инструкция хранения](../../deploy/README.md). Автоматический `migration-snapshots` содержит проверенный снимок базы и не заменяет полную эксплуатационную копию загрузок.
4. В отдельной закрытой тестовой установке проверяет миграцию на восстановленной копии, обе роли, переносы, JPG/PDF, версии/комментарии/решения и повторный вход. Пользовательские действия выполняет на специально разрешённом тестовом проекте.
5. Перед разрешённым обновлением останавливает старую службу и параллельные задания, делает финальную полную проверенную копию, затем запускает новый согласованный коммит. До открытия доступа проверяет журнал запуска, отсутствие ошибок миграции и сохранность счётчиков/оригиналов. Не выполняет `data:init`, очистку или массовое распределение файлов.

### Откат

При ошибке миграции транзакция возвращает прежние строки и структуру, а проверенный снимок остаётся на диске. Оператор проверяет журнал и целостность перед запуском прежнего релиза.

После успешной миграции старый код не поддерживает все операции с согласуемыми материалами без этапа. Поэтому простое переключение кода назад **не считается полным откатом функциональности**. Если после обновления ещё не было пользовательских записей, оператор может восстановить полную предрелизную копию в новую папку и вернуть прежний код/настройки. Если новые записи уже появились, сначала сохраняется текущее состояние; восстановление старой копии потеряет эти изменения и требует отдельного решения владельца. Предпочтительно исправление вперёд либо согласованный перенос новых данных. Прежняя папка никогда не удаляется и копия не накладывается поверх неё.
