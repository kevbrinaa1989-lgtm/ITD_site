# Файлы проекта — библиотека материалов и документов

Ветка `feature/project-file-library` основана на `39289b779a5b01108288ea8bb4c8ace53f0d15f7` из `fix/route-stage-progress`. Включены уже существовавшие в этой базе пакетная загрузка, реквизиты документов, приглашения, обзор кабинета и иллюстрации этапов. Этот PR не добавляет таблиц или миграций.

## Что показала проверка исходного интерфейса

- В «Материалах» большой альбом соседствовал с повторным списком тех же изображений. Исторические версии также попадали в общий список.
- «Документы» были отдельным разделом, а файлы этапов повторялись в карточках этапов. Для поиска приходилось переходить между несколькими местами.
- Форма загрузки находилась в управлении проектом и занимала много места; технические имена затрудняли просмотр документов.
- При этом сервер уже хранил привязку к этапу, версии и решения по конкретной версии, реквизиты документов и квитанции повторной загрузки. Перестройка хранения для новой библиотеки не нужна.

## Решение

Одно пространство «Файлы проекта» с переключателями **Все файлы / Материалы / Документы**. Материалы сгруппированы по этапам в компактную галерею. Документы представлены строками: понятное название, вид, номер и дата, этап, формат, размер, открытие и скачивание. Подробная карточка показывает реквизиты и исходное имя; JPG/PNG/WEBP/PDF открываются существующим просмотрщиком.

Поиск учитывает логическое название, этап, номер документа и исходные имена всех версий. Фильтры этапа и типа свёрнуты; сортировка использует порядок загрузки, название или дату документа. API не возвращает время загрузки, поэтому новые даты не выдумываются: порядок загрузки определяется существующим идентификатором файла.

Материал с несколькими версиями занимает одну карточку. Поиск старого имени открывает именно найденную версию в полноценном рабочем пространстве согласования. Решения, комментарии и ограничения старых версий сохранены. Возврат в библиотеку восстанавливает поиск, фильтры и позицию прокрутки. Альбом доступен отдельным режимом без одновременного дублирования карточек. Из этапа ведёт кнопка в библиотеку с нужным фильтром.

Загрузка открывается в диалоге: получатель, несколько файлов, раздел, этап, очередь и сворачиваемые реквизиты каждого документа. Видны ожидание, подготовка, отправка, успех и ошибка. После частичного успеха реквизиты сохранённых файлов заблокированы, повтор продолжает оставшуюся очередь. Существующий механизм квитанций защищает от копий при потере ответа сервера. Подготовленные файлы не переназначаются другому проекту незаметно.

## Границы изменений и данные

- `project-files.js` — проекция существующих данных без записи и изменения исходных объектов; `file-library.js` — отображение и навигация; `file-library.css` — оформление в системе «Маршрут».
- Сервер изменён только для выдачи трёх новых статических файлов. API, авторизация, роли, SQLite, реквизиты, связи и ограничения загрузки не изменены.
- Оригиналы не переименовываются, не перемещаются и не очищаются. Удаление остаётся существующим явным действием администратора с подтверждением; согласуемые материалы обслуживаются прежним механизмом согласования.
- Продуктивный проект не использовался: авторизованная сессия заказчика/администратора и копия его данных в этой среде отсутствуют. Проверка выполнена через настоящие API и временную SQLite с изолированным проектом и настоящими загруженными тестовыми файлами. Это не проверка содержимого продуктивной базы.
- На VPS и `lk.itdstudio.ru` изменения не публиковались. Слияние PR не выполнялось.
- Использованы сохранённые ориентиры Superdesign «Маршрут». Подключение подтверждено; новая генерация была недоступна из-за исчерпанных кредитов. Финальные иллюстрации ниже — снимки реализованного приложения в Chromium, не обещание нового макета на холсте.

## Проверки

- `npm test`: **209 / 209 PASS**. Семь новых проверок библиотеки: отсутствие дублей, доступность каждой версии, неизменность источника, реквизиты, поиск старого имени, фильтры и сортировка, документы без реквизитов.
- `browser-file-library`: **360, 390, 768, 1024, 1440 px**. Семь этапов, первый согласован с материалом, второй в работе; JPG/WEBP, PDF и TXT, старый PDF и текущая картинка одного материала, три документа, длинные строки. Проверяются фильтры, версия поиска, реквизиты, просмотр PDF, роли, очередь и повтор после потерянного ответа. Исходные записи и этапы сравниваются до/после, каждый оригинал скачивается с побайтовым сравнением.
- `browser-review`, `browser-route`, `browser-route-fixes`: пять заданных ширин, согласования конкретных версий, комментарии, прогресс, отсутствие переполнения и сохранение решений.
- `browser-upload-context`: 1440, 768, 430, 375 px; получатель, смена проекта, отмена/возврат, пакет документов и материалов, безопасный повтор и переназначение клиента.
- `browser-approved-interface`: 1440, 768, 430, 375 px; действующие пользовательские сценарии. `browser-preview`: локально 360 и 1440 px; изображения, PDF, увеличение, перемещение и доступ к скачиванию.
- Полный набор CI содержит серверные проверки и 11 браузерных наборов. Его итоговый статус указан в Pull Request; снимки CI доступны в артефактах каждого набора.

Браузерные проверки создают собственные временные данные и слушают только `127.0.0.1`. Внешние запросы страниц блокируются. При съёмке использовано публичное изображение из портфолио ITD; это иллюстрация тестового проекта, не данные заказчика.

## Проверка и будущая установка

В отдельной папке кода с Node.js 24 выполните `npm test`. Для браузера установите Playwright (`npm install --no-save --package-lock=false playwright@1.58.2`), укажите `ITD_CHROMIUM` на установленный Chromium/Chrome и выполните `node tests/browser-file-library.mjs`. Для всех наборов используйте команды из `.github/workflows/cabinet-checks.yml`. Не подключайте эти тесты к рабочей базе.

Публикация требует отдельного поручения владельца. До неё оператор должен сравнить установленный коммит с базой этого PR: здесь сохранены накопленные изменения ветки исправлений, а не только первоначальный редизайн. Не применяйте новую страницу без соответствующих JS/CSS из этого же релиза.

Резервирование и откат описаны в [инструкции обновления](../redesign/UPDATE-AND-ROLLBACK.md) и [инструкции хранения](../../deploy/README.md). Для этого релиза выбирается утверждённый коммит **`feature/project-file-library`**, а не старая ветка из примера. Перед переключением: полная резервная копия базы и загрузок штатной командой, проверка копии, фиксация прежнего релиза и настроек. При проблеме возвращается предыдущий каталог кода; данные автоматически не откатываются. Восстановление базы — только отдельное осознанное решение оператора, чтобы не потерять новые действия пользователей. Команды установки и отката в рамках этой работы не выполнялись.
