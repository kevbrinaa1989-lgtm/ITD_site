# Центр согласования ITD Studio

База изменений: `adf83c1773dbdcbe10d15bed759d131b496c112b`, ветка `feature/project-file-library` (включая исправления принадлежности документов из PR №4). Изменения подготовлены в `feature/approval-center`. Рабочий сервер, рабочая БД и публичный сайт Tilda не изменялись.

Статус: реализация и доступные автоматические проверки подготовлены для ревью. Приёмка на физических Android/iOS остаётся обязательной до выпуска. WebKit на Linux и подмена User-Agent не заменяют Samsung Internet и Safari на телефоне.

## Что изменилось

- В существующей вкладке согласований: список с поиском, структурированными помещениями, фильтрами и массовым выбором; просмотр; решения и замечания. На телефоне — отдельные панели «Материалы», «Просмотр», «Замечания и решение».
- Решения сначала сохраняются серверным черновиком. Подтверждение сводки отправляет пакет одной транзакцией. Конфликт любой версии отклоняет весь пакет; повтор операции не дублирует решения, уведомление или ведомость.
- Просмотр текущей версии подтверждается отдельно; для PDF сервер определяет реальное число страниц. Массовое и одиночное согласование требуют просмотра. Старый API решения также проверяет это условие.
- Маркеры привязаны к версии и странице, используют координаты 0–1. До отправки их можно исправить/удалить, после отправки исходный текст и координаты неизменяемы. Дополнения и смена статуса записываются событиями.
- Дизайнер описывает новую версию и судьбу каждого открытого замечания. Его отметка «исправлено» не закрывает замечание: клиент отдельно подтверждает исправление и отдельно принимает новую версию файла.
- Сравнение соседних версий рядом, синхронный просмотр, ползунок для изображений одинаковых размеров. Несовпадение размеров и числа PDF-страниц обозначается явно; маркеры остаются на своей версии.
- Раунды, неизменяемые ведомости с PDF-выгрузкой; отдельное принятие этапа с перечнем препятствий. По умолчанию материалы обязательны, дизайнер может явно назначить дополнительные.
- Дизайнерская очередь замечаний по выбранным проекту/этапу, с фильтрами материала и статуса. Публикация выбранных существующих файлов на согласование одним пакетом создаёт одно уведомление.

Существующие загрузка с привязкой к контексту, документы, библиотека файлов, скачивание, права доступа, уведомления и старые обсуждения сохранены. Ручное административное изменение статуса этапа в существующем разделе управления остаётся административным действием; оно не создаёт событие клиентского принятия этапа.

| `approval-center.js`, `approval-center.css` | Интерфейс внутри текущего кабинета; восстановление черновика, очереди, адаптивные панели |

| `server.mjs`, `material-review.mjs` | Подключение маршрутов, отчёт в существующей загрузке, общие события/права, отдельное принятие этапа |
| `cabinet.html`, `material-review.js`, `client-workspace.js` | Подключение UI, переходы из библиотеки/уведомлений, подписи новых событий |

| Изменённые существующие тесты | Новое отдельное принятие этапа, обязательный просмотр и новые селекторы UI; прежние проверки сохранены |

Источники истины для проектов, этапов, файлов, версий, авторизации и уведомлений — прежние таблицы и модули. Новые файлы не копируют физические оригиналы. Все превью/шрифты/PDF.js загружаются с того же сервера. Ведомость использует существующий кириллический шрифт `assets/fonts/itd-font-1.ttf`.

Миграция при запуске добавляет 11 таблиц `approval_*`: `metadata`, `drafts`, `view_pages`, `view_confirmations`, `preview_metadata`, `packages`, `notes`, `note_events`, `corrections`, `publications`, `stage_events`. Добавляются индексы и триггеры неизменяемости. Прежние строки, файловые пути, принадлежность документов и история не переписываются. Повторный запуск безопасен. Исключение из прежнего поведения: согласование последнего обязательного файла больше не означает автоматического согласования этапа.

## API

Все маршруты требуют существующую сессию; изменения — прежнюю проверку Origin/CSRF. Доступ проверяется по текущему владельцу проекта; клиент не может действовать от имени дизайнера или чужого проекта.

| Маршрут | Метод и действие |
|---|---|
| `/api/approval-center/projects/:projectId/stages/:scope` | GET: материалы, версии, заметки, черновик, конфликты, препятствия, ведомости |
| `…/draft` | PUT: `expectedRevision`, `entries`, `position` |
| `…/submit` | POST: `operationId`, `expectedRevision`, `confirm`; атомарная отправка |
| `…/publish` | POST, администратор: `fileIds`, `operationId`, `confirm` |
| `…/approve-stage` | POST, клиент: `operationId`, `token`, `confirm` |
| `/api/approval-center/versions/:id/view` | POST: отрисованная `page`, затем отдельное `confirm`; для неподдерживаемого превью `downloaded` |
| `/api/approval-center/materials/:id/metadata` | PATCH, администратор: помещение, обязательность, `expectedRevision` |
| `/api/approval-center/notes/:id/events` | POST: тип, пояснение, ревизия, версия |
| `/api/approval-center/packages/:id` | GET: исторический снимок |
| `/api/approval-center/packages/:id/pdf` | GET: PDF исторического снимка |
| Существующий `/api/projects/:id/files` | При новой версии: `correctionReport.description` и `resolutions` по открытым замечаниям |

`scope=0` обозначает материалы проекта без этапа, а не все этапы. При смене версии/принадлежности старый черновик не применяется к новой версии. Страница сообщает конфликт; локальная резервная копия доступна через «Восстановление черновиков». Она дополняет серверный черновик, не подменяя его.

Уведомления идут через существующие `review_events`/`review_notifications`: одна отправка клиентского пакета — одно уведомление студии. Публикация существующих файлов пакетом — одно уведомление клиенту. Индивидуальная загрузка новой версии и отдельный отчёт исправлений сохраняют события своих операций.

## Производительность и границы

Оригиналы всех материалов не загружаются одновременно: активный просмотр, максимум две видимые миниатюры до 2 MiB и предзагрузка одного следующего файла до 2 MiB. При смене материала задачи/рендер отменяются; canvas ограничен по разрешению. Метаданные выбранного этапа приходят одним ответом; для 100 материалов есть серверная и браузерная проверка. Предварительный просмотр больших оригиналов по-прежнему ограничен существующим лимитом загрузки приложения.

Сервер проверяет число PDF-страниц и сохранённые подтверждения. Он не может доказать, что человек прочитал содержимое: UI требует успешной отрисовки и отдельного явного подтверждения. Это не электронная подпись.

Для совместимости старые вызовы загрузки новой версии без открытых маркерных замечаний принимаются без отчёта. Новый интерфейс всегда требует описание изменений; при открытых замечаниях отчёт обязателен и на сервере.
