# Установка и откат — только после отдельного разрешения на публикацию

Ни один приведённый шаг не выполнялся на рабочем сервере. Точный путь релиза, имя службы и способ переключения определяет существующая конфигурация размещения; выдуманные команды VPS не приводятся.

## Перед выпуском

1. Завершить ревью PR и обязательные проверки на реальных Samsung Internet/Android, Chrome/Android и Safari/iPhone. Не считать подмену User-Agent результатом этих проверок.
2. Зафиксировать SHA текущего релиза и расположение постоянного хранилища. Убедиться, что база соответствует поддерживаемой версии; сравнить с базой PR `adf83c1773dbdcbe10d15bed759d131b496c112b`.
3. Приостановить изменения пользователями, штатно остановить службу. Из текущего окружения приложения выполнить `npm run backup -- /абсолютный/путь/копий`; затем `npm run backup:verify -- /путь/созданной/копии`. Проверить наличие БД, originals/files и манифеста; сохранить копию вне сервера. Сохранить конфигурацию окружения отдельно с прежними закрытыми правами.
4. В отдельной папке подготовить новый релиз на Node.js 24.13–24.x, установить `npm ci`. Не запускать первоначальную настройку и не создавать новую рабочую БД.
5. На изолированной восстановленной копии проверить запуск, права, авторизацию и сохранность документов/версий. Восстановление — только в **новую** папку: `npm run backup:restore -- /путь/копии /новая/папка`. Старые сессии в восстановленной копии штатно отзываются. Не направлять тестовый экземпляр на рабочие данные.
6. После разрешения переключить релиз штатным способом с прежней конфигурацией хранилища. Первый запуск добавит таблицы/индексы/триггеры `approval_*`; прежние записи не удаляются и не переназначаются.
7. Проверить вход обоих ролей, документы без этапа и внутри этапа, оригиналы, версии, сохранение черновика, ведомость/PDF, уведомления. Отдельно проверить завершение этапа и запись события клиентского принятия. После проверки вернуть доступ пользователям.

## Откат

При ошибке остановить изменения и службу, сохранить **новую** проверенную копию текущего состояния с данными, созданными после выпуска. Сохранить журналы ошибки без паролей/сессионных cookie.

Предпочтителен откат кода на прежний SHA с сохранением текущего хранилища: новая схема добавочная, старый код не читает таблицы `approval_*`. Не удалять эти таблицы и не применять разрушительные обратные миграции. После отката держать новые согласования приостановленными до решения, поскольку старый интерфейс не отображает новые маркерные замечания/ведомости, а старый код автоматически принимает этап по файлам. Прежние оригиналы, документы и версии должны оставаться доступны.

Восстановление предрелизной БД может потерять изменения после выпуска. Оно не является автоматическим шагом: требуется отдельное согласованное решение о данных. Восстанавливать в новую папку, проверить её и только затем переключать конфигурацию. Исходную и новую резервные копии сохранять. Никогда не копировать поверх работающей SQLite и не удалять оригиналы.
